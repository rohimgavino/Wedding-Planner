## Actual server bypass risk (source review, not hosted posture)

`202610140001_workspace_entitlements_savings.sql` creates private `release_controls.sales_activation=false`, enables deny-default RLS and denies API grants on that gate table; paid-planner restrictive policies are held separately in `supabase/activation/paid-enforcement.sql`. `202610140002_admin_manual_purchases.sql` grants authenticated EXECUTE on legacy request/verify/settings functions. Request requires workspace membership, settings `sales_enabled`, and the sales activation gate (lines 69–80). Verify requires site admin and gate, explicit dashboard confirmation, matching amount/reference and locks; it then creates/extends entitlements (82–104). Settings requires admin and the gate when enabling sales (34–42). Reject is admin-authorized but not sales-gated (105–116); it changes history, not access. Developer-role migration replaces role checks but does not replace these purchase bodies.

**Client cleanup does not disable direct RPC calls.** If hosted functions match these files and gate/settings are enabled, a member can still request a legacy purchase via REST and an authorized admin can manually verify one. Verify does not require `site_settings.sales_enabled`; merely setting that false cannot stop verification. No actual hosted gate/definition was inspected here. Missing release-controls singleton is also unsafe: scalar subqueries return NULL and PL/pgSQL `IF NOT NULL` does not reject. Source defaults therefore are not hosted proof of fail-closed enforcement. Existing restrictive tenant and entitlement checks remain unchanged; this is not an anonymous self-grant claim.

Before declaring DOKU-only enforcement complete, independently inventory hosted definitions/grants/gate with approved read-only access and coordinate with the backend candidate. If legacy execution remains possible, review a separate explicit server disabling migration: replace request/verify/save-with-enabled bodies with unconditional legacy-sales-unavailable errors (retain support/history read capability separately), revoke API execution where compatible, and regression-test authenticated/admin direct calls, old entitlement survival and read-only history. Do not rely only on revoking API grants if a privileged callable adapter still invokes legacy functions. Prefer an explicit provider-specific gate with `IS DISTINCT FROM true` and required singleton existence for future DOKU code. Do not reuse the shared sales gate if it would reopen legacy paths. No SQL migration is included/applied here; parent/backend review must resolve policy and concurrency with the separate backend release.
